# Languages

The public site is published in ten languages: Arabic, English, and eight European ones — German,
Spanish, French, Italian, Dutch, Portuguese, Russian and Turkish.

The dashboard is not translated. It is an internal tool used by an Arabic-speaking team, and
carrying it through ten dictionaries would be maintenance with no reader.

## The one thing to understand first

There are two layers of text on this site and they do not speak the same number of languages.

| Layer | Where it lives | Languages |
|---|---|---|
| Interface — menus, buttons, labels, errors, headings | `src/i18n/locales/*.js` | all ten |
| Content — services, projects, team profiles, testimonials, FAQs, and the 39 marketing texts the dashboard owns | the database, as `_ar` / `_en` column pairs | Arabic and English only |

So a visitor reading the site in German gets a German interface wrapped around English content. That
is the intended result, not a gap waiting to be filled.

`src/i18n/languages.js` is where this is written down. Every locale carries a `content` field naming
the database column it reads, and for the eight European ones that field is `en`:

```js
{ code: 'de', label: 'Deutsch', dir: 'ltr', content: 'en' }
```

Delete that field and `pick(project, 'name')` starts looking for `name_de`, finds nothing, and every
card on the site renders empty. Nothing throws. That is why it is data in one file rather than a
condition spread across twenty components, and why `ui.test.js` asserts that no locale ever points
at a third column.

## Changing a text

**Interface text** — edit the key in all ten files under `src/i18n/locales/`. `ui.test.js` fails the
build if a key exists in one file and not another, so a half-finished edit cannot ship.

**Content** — edit it in the dashboard, in Arabic and English. It reaches the Arabic and English
sites immediately.

**The catch.** The dashboard owns 39 of the most visible texts on the site: the hero, every section
heading, the entire About page, the footer. Those edits do *not* reach the eight European locales —
they keep rendering from `src/i18n/locales/*.js`.

This is deliberate. The alternative was to fall back to the dashboard's English, which would have
put an English hero, English section headings and an English About page inside an otherwise German
site. A whole page in one language is worth more than a page that is current in half of it.

The cost is real, though: **change one of those 39 texts in the dashboard and the eight locale files
need the same change by hand.** They are:

```
heroBadge  heroT1  heroAccent  heroSub  heroCta1  heroCta2  intro
servicesKick  servicesTitle  servicesSub  servicesAll
featuredKick  featuredTitle  processKick  processTitle  processSub
testimonialsKick  testimonialsTitle  partnersKick  partnersTitle
faqKick  faqTitle  ctaTitle  ctaSub  ctaBtn
portfolioTitle  portfolioSub  contactTitle  contactSub
aboutTitle  aboutStory  visionT  vision  missionT  mission  valuesT  whyT
footTagline  footRights
```

## Adding a language

1. Copy `src/i18n/locales/en.js` to `src/i18n/locales/<code>.js` and translate it.
2. Import it in `src/i18n/ui.js`.
3. Add a row to `LANGUAGES` in `src/i18n/languages.js`, with `content: 'en'`.
4. Run the tests. `ui.test.js` will name any key you missed.

If the language is not written in the Latin or Arabic script, check that Poppins covers it. It does
not cover Cyrillic, which is why `src/index.css` swaps in Montserrat under `html[lang="ru"]`; Greek,
Hebrew or Devanagari would each need the same treatment.

## Which language a visitor lands in

In order:

1. A language they picked before, remembered in `localStorage` under `ngp.lang`.
2. Their browser's language — **but only if it is one of the eight European ones**.
3. Arabic.

English is deliberately excluded from step 2. An English-locale phone is ordinary among this
company's Arabic-speaking audience, so treating it as a request for the English site would pull the
primary audience out of its own language. A browser reporting Dutch carries no such ambiguity.

To auto-detect English as well, add `'en'` to `AUTO_DETECT` in `src/i18n/LanguageContext.jsx`.

## Search engines

Google indexes the Arabic site only. The language is chosen in the browser and stored locally; it
never appears in the URL, so there is no separate address for a crawler to index and no `hreflang`
to declare. The eight locales serve visitors who arrive at the site, not visitors who find it by
searching in German.

Changing that means putting the locale in the path — `/de/services` — along with per-locale
sitemap entries and `hreflang` tags. It is a larger piece of work and has not been done.

## What it costs

The ten dictionaries are bundled together, about 22 KB gzipped for the eight new ones, roughly a
sixth of the JavaScript the site ships. Every visitor downloads all ten and reads one. Splitting
them into chunks loaded on demand would recover most of it, at the price of a visible flash of the
wrong language for anyone auto-detected into a European locale on first paint.
